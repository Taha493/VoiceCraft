# VoiceCraft: measured performance and limitations

All numbers below were measured on the target laptop on 2026-10-24:

- CPU: Intel Core i5-1035G1 (4 cores / 8 threads, 15 W), on battery
- RAM: 7.4 GiB total, typically **2.2–3.7 GiB free** with a desktop session open
- OS: CachyOS (Linux 6.18), Python 3.12 via uv, FFmpeg 9.0.1

Nothing here is a projection. Where a number depends on machine load, the load is stated.

## 1. Choosing the TTS engine

Script: `bench/tts_bench.py`. Each engine runs in its own process. The test is 10 representative narration lines (about 37 s of speech), synthesized twice; the second, warmed-up pass is reported. The CPU was otherwise idle and inference used 4 threads.

| Engine | Real-time factor (lower is faster) | Peak RAM | Notes |
|---|---|---|---|
| **Kokoro v1.0 ONNX fp32 + misaki G2P** (default) | **0.70** | **787 MB** | Same G2P as the reference model |
| Kokoro v1.0 ONNX fp32 + espeak-ng G2P | 0.70 | 655 MB | Slightly weaker pronunciation |
| Kokoro v1.0 ONNX fp16 + misaki | 0.70 | 823 MB | No benefit on CPU |
| Kokoro v1.0 ONNX int8 | 1.74 | 431 MB | Dynamic-quant kernels are slow on this CPU |
| Kokoro 0.9.4 reference (PyTorch CPU) | 1.29 | 1455 MB | First call downloaded ~330 MB from Hugging Face |
| Piper 1.8, `en_US-joe-medium` | 0.08 | 334 MB | About 9× faster; flatter, more robotic voice |

Thread scaling for Kokoro fp32: 2 threads gives RTF 0.86, 4 threads 0.70, 8 threads 0.91 (hyper-threads oversubscribe). The default is 4.

**Decision:** Kokoro ONNX fp32 with misaki is the default. It is faster than real time with peak memory under 0.8 GB, which leaves headroom on 8 GB. Piper is an optional extra for speed. Listen to the samples in `bench/out/*.wav` (generated by the script) to compare quality yourself.

One finding during the evaluation: `misaki[en]` pulls in `spacy-curated-transformers`, which makes spaCy import PyTorch at load time (+340 MB). VoiceCraft lists misaki's English dependencies by hand to avoid it.

## 2. End-to-end pipeline

Script: `bench/pipeline_bench.py`. It uses synthetic "Claude-style" videos from `bench/make_test_video.py`, which include the things that break naive detectors:

- an animated gradient background, a static title, and a mid-screen label that changes;
- fade-in captions and typewriter (word-by-word) captions;
- every fifth caption deliberately too short to speak.

Each video starts with an empty TTS cache.

### Accuracy (identical across runs)

| | 30 s · 720p · background music | 60 s · 1080p · silent |
|---|---|---|
| Captions found | 9 / 9 | 19 / 19 |
| Character error rate | 0.0 % | 0.0 % |
| Caption start error | mean 0.09 s, max 0.17 s | mean 0.08 s, max 0.17 s |
| Caption end error (max) | 0.10 s | 0.12 s |
| Voice starts after caption appears | max 0.39 s | max 1.07 s (a line may start up to 0.8 s late instead of freezing the picture) |
| Voice starts while its caption is visible | 9 / 9 | 19 / 19 |
| Overrun handling (current planner) | 1 held, 0 flagged | 2 held, 0 flagged (first version: 5 held) |
| Speech onset in rendered file vs plan (max) | n/a (music masks silence) | 0.075 s |

The voice-after-caption delay is mostly intentional: the "pitch" preset waits 0.2 s after a caption appears. The remaining ≤0.17 s comes from sampling at 4 frames per second.

### Speed and memory

Peak RAM per stage, the same in all runs:

| Stage | Peak RAM |
|---|---|
| Captions | 300–310 MB |
| Narrate | 680–691 MB |
| Render | ~55 MB |

Each stage runs in its own process and releases its memory on exit. The API server itself uses about 45 MB.

**Run A: lightly loaded machine.**

| Video | Captions | Narrate | Render | Total |
|---|---|---|---|---|
| 30 s · 720p | 24.9 s | 25.5 s | 11.0 s¹ | **61 s** (2.0× video length) |
| 60 s · 1080p | 28.2 s | 17.9 s² | 58.5 s¹ | **105 s** (1.7×) |

¹ x264 preset `fast`. ² Shared cache, so 16 of 25 clips came from the 30 s run.

**Run B: busy desktop, final code.** A browser tab was using 110 % CPU (load average 12.5) and each video had a fresh cache.

| Video | Captions | Narrate | Render | Total |
|---|---|---|---|---|
| 30 s · 720p | 46.5 s | 46.4 s | 14.8 s | **108 s** (3.6× video length) |
| 60 s · 1080p | 45.1 s | 74.4 s | 50.1 s | **170 s** (2.8×) |

**Render preset.** Re-encoding the 60 s 1080p video with one frame hold took 50.0 s with x264 `fast` and 24.8 s with `veryfast`. File sizes were 14.9 MB and 11.9 MB, and the two outputs are visually identical (SSIM 0.9988). `veryfast` is now the default. When no frame is held, the video stream is copied and the render takes a few seconds.

**Caching.** Re-narrating after editing one caption regenerates exactly one clip; the rest come from the cache (covered by `tests/test_e2e.py`).

**Takeaway:** on this laptop, expect roughly **2–3.5× the video's length** to go from silent video to narrated MP4, depending on what else is running. That is not real time, and VoiceCraft doesn't claim it is.

### Real video: "CaptionDock Showcase"

This is a real 40 s portrait video (1536×1920, H.264, silent). It has headline captions at the top, short callouts at the bottom, and a screen recording in the middle. That recording shows a captions app, so it contains large, constantly changing transcript text.

| | First version (single band) | Current (size-aware, multiple bands) |
|---|---|---|
| Caption area found automatically | Wrong: picked the screen recording's subtitles (y≈0.59) | Top headlines **and** bottom callouts; the screen-recording text is rejected as a "text wall" |
| Captions narrated | 6 (the user set the area by hand) | 9 caption moments (10 lines; one staggered pair merged into a sentence) |
| Frame holds | none | none (the video is copied, not re-encoded) |
| Captions stage | 11 s (one band) | 33 s (two bands, 28 OCR reads) |
| Final loudness / true peak | voice only | −16.1 LUFS / −1.8 dBTP with music |

Still missed: the centered end card ("CaptionDock / Video captions that stay on top while you work"). It appears where the screen recording was and is dropped along with it. Add it with "Add caption" if you want it spoken.

What changed because of this video:
- Caption candidates must be *large*: at least 55% of the tallest text's height.
- Four or more closely stacked bands of large text count as screen content.
- Several caption bands are tracked independently, and lines that appear within 0.6 s of each other in different bands are read as one sentence.
- The planner lets a line start up to 0.8 s late before it freezes a frame. On the 60 s synthetic video that cut holds from 5 to 2.

## 3. Background music

**Choosing the library.** I downloaded 33 candidate tracks from incompetech.com (Kevin MacLeod, CC BY 4.0) and measured each one: tempo, brightness, mean energy, and loudness variation over the whole track and over the first 90 s, which is what most videos use. Tracks were rejected if they had near-silent sections or big level jumps (whole-track variation of 28–64 dB: Equatorial Complex, Perspectives, On My Way, Eternal Hope, Thinking Music), were too short to cover a video without looping (Bright Wish, 41 s), or leaned novelty rather than background. That left 14 tracks, 6 per mood, all 2–7 minutes long.

**Mix measurements** on the 20 s pitch video, with three consecutive renders picking three different tracks:

| Track (source loudness) | Final loudness | True peak | Music alone (pauses) vs. speech |
|---|---|---|---|
| Wholesome (−16.5 LUFS) | −15.9 LUFS | −2.6 dBTP | 10.2 LU below speech |
| Fearless First (−7.4 LUFS) | −15.9 LUFS | −2.6 dBTP | 10.3 LU below speech |
| Easy Lemon (−15.9 LUFS) | −15.9 LUFS | −2.9 dBTP | 8.1 LU below speech |

The source tracks span 14 LU (−7.4 to −21.2 LUFS), but each is brought to the same bed level before mixing. While the voice speaks, the music ducks a further ~9 dB (measured with test tones), which puts it roughly 18–20 dB under the voice. That's the usual broadcast range. A 12 s track under a 31 s video loops with 3 s crossfades and leaves no gaps. Audio and video lengths match exactly.

## 4. Offline operation

`unshare -rn voicecraft run …` runs the full pipeline inside a network namespace with no interfaces, using an empty TTS cache. It succeeds (`tests/test_e2e.py::test_pipeline_runs_without_network`). After `voicecraft setup`, processing needs no network.

## 5. Known limitations

- **Only one real video tested so far.** Accuracy numbers come from synthetic videos with known ground truth, plus the one real showcase video above. Other real exports may use smaller fonts or unusual layouts. The region editor and caption/script import are the fallbacks.
- **Captions inside the screen-recording zone.** Large text in the middle of a frame that is mostly screenshot (such as a centered end card) is dropped along with the screenshot text.
- **Animated backgrounds behind captions.** If the area behind the captions changes every frame, the change gate can't skip OCR. It then reads every sample, about 0.25 s each, so the captions stage gets slower but stays correct.
- **No emotion control.** Kokoro and Piper have no emotion or style controls. Presets only change pace, pauses and how soon the voice comes in. Questions and exclamations get whatever intonation the model produces from the punctuation.
- **Frame holds lengthen the video.** Holds change the duration (+1–2 s per minute in these tests) and force a re-encode. Turn them off to keep the exact original timing; long lines are then flagged.
- **Music was chosen by measurement, not by ear.** Steadiness, loudness and length were measured, but I couldn't listen to the tracks. Use Shuffle or pick a specific track if one doesn't suit a video.
- **Tesseract was not benchmarked.** It isn't installed on this machine (installing it needs root). RapidOCR is the default and is fully local; the Tesseract backend exists but hasn't been compared.
- **English only.** The voices, text normalizer and OCR are set up for English.
